# 后续工作安排

> 维护者计划。每项写明是什么、为什么、怎么做、做完怎么算闭环。
> 不收录已完成的工作；历史证据见[归档](../archive/)。

## 怎么用这份计划

- **一批一个 OpenSpec change**，走完整闭环：建 change → 实施 → 六道门禁 → 同步规格 → 归档 → 提交推送 → CI 双平台绿。
- **按价值排序，不按依赖排序**。只有真正被阻塞的项才往后放。
- **闭环判据是门禁通过，不是"看起来做完了"**。判据不明确的项，先把判据写清楚再动手。

每批的六道门禁：

```bash
python3 tools/check-framework
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -v
openspec validate --all --strict --no-interactive
openspec validate --archived --no-interactive
python3 tools/check-changes
git diff --check <base>...HEAD
```

`python3 tools/pre-commit-check` 是这六道在本地的一次性版本，提交前跑它，提交后跑 `--committed`。

## 1. 真实项目接入验证（最高优先，需要你给一个项目）

**是什么**：拿一个真实的业务项目跑一遍完整接入——`BOOTSTRAP.md` 的通用入口、模块下载、关系地图、资料生成、规格与实现、评审、验证、交付。

**为什么**：**这份计划最初写错了前提。** 当时写的是"所有证据都来自它自己和自己造的合成样例，没有一项在真实项目上跑过"。2026-11-01 复查后确认不对：工作区里有三个真实项目接过公共壳——`61.videohao-generator`（207 个源文件、101 个测试文件，5 个 change、69 个已完成任务）、`23.auto_cut`（1 个 change、7 个已完成任务）、`prntscr-web`（逆向项目，6 份真实逆向分析）。`docs/guide/from-zero-to-one.md` 的图文版验证记录也早于这次复查。

**但没有一个走完闭环**，这才是真问题：三个项目的 `openspec/specs/` 与 `openspec/changes/archive/` 全空，doctor 一律报 `initialization=PARTIAL` 与 `handoff=READY_FOR_PLANNING`。videohao 还有 43 项改动从未提交，两个 change 目录从未进 git。**"做"发生了，"收"没发生。**框架的成熟度不能靠技能数量量，只能靠真实项目里闭环的数量。

**怎么做**：
1. 你提供一个真实项目（仓库地址或本地路径）与模块划分——或者授权直接用 `61.videohao-generator` 收口。
2. 用当前 `main` 做一次完整接入，过程产物落在项目里，不污染本仓库。
3. 按 `docs/guide/from-zero-to-one.md` 的 15 条工作流走一遍真实任务，而不是走初始化。
4. 走完把规格同步进 `openspec/specs/`、把 change 归档，让 doctor 不再报 PARTIAL。

**闭环判据**：真实项目完成一次新行为（规格 → 计划 → 实现 → 评审 → 验证 → 集成），**并且**规格已同步、change 已归档、doctor 不再报未完成状态；接入过程中的问题被逐条记为 change 或修复。

**阻塞**：需要你提供项目，或授权使用已有项目。这条不做，后面的都是纸面功夫。

## 2. 知识回流机制的真实验证

**是什么**：在本仓库（或接入的项目）里真正跑一次 llm-wiki 的知识回流：解决一个问题 → 判定归属模块 → 摄入 → 校验 → 下次检索得到。

**为什么**：知识回流是框架的核心机制之一，但**本仓库没有 `knowledge/` 目录**——这套规则从来没有在真实使用中被验证过。`docs/framework/knowledge-policy.md` 规定了模块路由、写入授权、来源与推理分离，但全是规定，没有实践。

**怎么做**：
1. 挑一个已解决的真问题（例如本次会话里的"keychain 阻塞推送"或"引入技能漏带 agents/openai.yaml"）。
2. 按知识策略判定归属与授权，摄入对应模块库。
3. 换一个会话验证检索得到，且确认 `ingestion` 状态与实际一致。

**闭环判据**：知识页、索引与日志都真实存在且被检索命中；写入授权被明确记录。

## 3. `tools/verify-live` 的真实验收复跑

**是什么**：跑一次显式开启的真实验收探针（`tools/verify-live`）。

**为什么**：它覆盖接入、初始化、规格校验与 doctor 路径，是唯一对真实源码做端到端验收的工具。0.2.0 之后没有再跑过。

**边界要说清楚**：它**不覆盖**这轮改动落到的计划、评审、测试三个阶段的技能绑定。那三处目前只有契约测试与人工走查，没有端到端探针。想补的话是另一项（第 4 项）。

**闭环判据**：一次真实运行的完整输出，且失败项逐条归因。

## 4. 计划与评审阶段的端到端探针

**是什么**：给 `tools/verify-live` 增加对计划阶段（切片写入 `tasks.md`、阻塞边）与评审阶段（两轴评审、Spec 轴来源是 OpenSpec change）的探针。

**为什么**：这轮把计划阶段的核心产物从"计划文档里的微步骤"改成了"`tasks.md` 里的垂直切片加阻塞边"，把评审阶段从"单评审者"改成"双轴"。两处都是**流程语义**的改动，却只有契约测试覆盖——契约测试能证明配置写对了，证明不了流程跑得通。

**怎么做**：仿照现有的 `spec-validation`、`new-doctor` 步骤，加两个合成步骤：一个构造一个含阻塞边的 change 并检查切片写入与覆盖度，一个构造一次双轴评审并检查两轴分别产出。

**闭环判据**：新步骤在 `verify-live` 里通过，且覆盖"规格来源缺失时如实报无可用规格"这条分支。

## 5. 两个旧 change 的最终归宿（需要你决定）

**是什么**：`add-project-bootstrap-and-maps`（24/25）与 `agent-led-project-intake`（12/29）的最终处置。

**为什么**：它们的任务缺口是真实宿主、跨宿主恢复、私有认证与远端 CI 证据——本环境拿不到，所以按框架自己的归档门禁（全部适用门禁完成）不能归档。它们一直挂在活动区，而 `openspec validate --archived` 也不检查活动区，所以这个状态可以无限期存在。

**三个选项**：
- **继续推**：在有真实宿主的环境里补证据，然后走正常归档流程。成本最高，收益是让两个核心能力真正封口。
- **明确封存**：把剩余任务标注为"本环境不可达"并保留在活动区，同时在 `docs/maintainer/legacy-change-status.md` 写明这是最终状态而非待办。成本低，但"未完成"会永久留在仓库里。
- **拆分**：把纯文档与代码类任务拆出来单独走一轮，只把真实验证类留在原地。

**闭环判据**：选定方案写进 `docs/maintainer/legacy-change-status.md`，并让检查能区分"待办"与"已封存"。

**阻塞**：需要你选。

## 6. 规格库与阶段路由的一致性复核

**是什么**：把 `openspec/specs/` 的 32 份能力规格与 `AGENTS.md` 的阶段路由表逐条对照，找出"规格存在但没有阶段用它"和"阶段用了但规格缺失"。

**为什么**：规格库和阶段表是两套手工维护的真相，这轮连续替换技能时已经出现过偏差（`AGENTS.md` 里"另有两个参考技能"在 matt-pocock 扩到 8 个后就过时了，靠人读出来的；2026-11-01 又出现"引入 `domain-modeling` 却没接路由"）。32 份规格对 11 行阶段表，人工对不完。

**怎么做**：写一个只读核对工具——读阶段表里点名的技能，反查它们对应的能力规格；读规格的 capability 名，反查它属于哪个阶段。报出对不上的。

**闭环判据**：核对工具进 CI，差异为零。

## 7. 15 条工作流指南与现技能的一致性复核

**是什么**：复核 `docs/guide/from-zero-to-one.md` 的 15 条工作流在技能替换后是否还准确。

**为什么**：这轮换掉了实现、计划、排障、评审四个阶段的技能，指南里 15 条工作流的提示词与流程描述可能已经与实际路径不一致。初步扫过，指南用的是通用表述（"TDD"）而不是技能名，所以看起来一致——但那是抽样，不是复核。

**现在有了落点**：2026-11-01 的技能接线批次给指南第二部分补了「每条工作流用到的技能」表，15 条工作流与阶段路由表的对应关系第一次写下来了。逐条走查可以从这张表开始，差异会被具体到"这条工作流背后该站哪个技能"，而不是笼统的"看起来一致"。

**闭环判据**：15 条工作流逐条走查，每条要么确认一致，要么记录差异并修。

## 8. 两个待移除技能与实施阶段的并行委派缺口

**是什么**：两件事，都需要你拍板。

**一、建议按先例移除两个技能**
- `superpowers:using-superpowers`——它的职能是"任何回应之前先查技能表"，而框架已用阶段路由表加 `skill-policy.md` 取代这一层；它"哪怕 1% 可能适用就必须调用"的要求与框架"只加载本任务需要的技能"实质冲突。
- `superpowers:subagent-driven-development`——它的 task reviewer 是"规格符合性 + 代码质量"两轴，与 REVIEW 阶段的 `matt-pocock:code-review` 同一判据两套实现；implementer 自行提交与"提交权在 INTEGRATE 阶段由用户选"冲突。框架已有先例：被取代的三个上游技能已从包里彻底移除。

**二、实施阶段仍无并行委派落点**
`executing-plans` 是顺序执行，`subagent-driven-development` 不接，`dispatching-parallel-agents` 只管排障阶段的并行分解。`skill-policy.md` 写着"并行子任务仅在宿主支持且当前指令授权时执行"，但执行细则只有排障那一条。

**为什么**：模型调用型技能的描述常驻上下文，每个回合都付预算。留在包里又不点名的技能，是纯开销。

**怎么做**：确认后从分发移除这两个技能，同步更新清单与技能计数。若要补实施阶段的并行委派，应写本地改编层（评审走 `matt-pocock:code-review`、提交走 INTEGRATE 阶段），而不是引入第二套评审机制。

**闭环判据**：两个技能的去留写进本文件；分发清单的技能计数与实际入口数一致。

## 需要环境或授权才能做的事

| 事项 | 阻塞在哪 |
|---|---|
| 真实宿主 / 跨宿主恢复证据 | 需要对应的宿主环境与授权；两个旧 change 的归档门禁依赖它 |
| 私有源认证 | SSH 接口有离线回归，真实私有源未验收；HTTPS credential helper 不自动加载 |
| 真实设备 / 部署 | 框架不预建业务设备适配器，需具体项目提供 |

这些不是仓库能自己解决的，写在这里是为了别被当成"待办"漏掉。

## 明确不做（附理由，避免反复讨论）

- **不引入上游的编排型技能**（`to-spec` / `implement` / `implement-spec` / `wayfinder` / `triage` / `setup-matt-pocock-skills`）：它们是与 OpenSpec 竞争的规格体系，且依赖 issue tracker。
- **不引入上游的 issue-tracker 依赖族**（`ask-matt` / `grill-with-docs` / `improve-codebase-architecture` / `teach` / `to-questionnaire` / `wait-what` / `harness` 等）：路由目标不存在或是个人工作流形态。
- **不引入上游 `misc/`（4 个）与 `in-progress/`（7 个）**：上游自述冻结或未稳定。
- **不建独立 ADR 集合**：OpenSpec change 的 design 产物与 `docs/project/architecture.md` 已经是决策记录，再来一套就是第二个来源。
- **不追溯改造既有技能的形态声明**：形态机制前向落地，新技能按需选用，存量技能保持现状。
