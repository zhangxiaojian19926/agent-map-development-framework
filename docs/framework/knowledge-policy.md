# 公共知识库访问、建立与模块回流

本文件只规定方法与权限,不列任何项目的实际模块、alias 或 KB 路径。实际映射、注册表和命令见项目资源文档。沿用 §11.x 编号便于旧引用迁移。

## 11. KNOWLEDGE 阶段(llm-wiki 路由)

> 顶层 AGENTS.md §0 定义查询时机;同一阶段复用结果,范围或证据变化时重新查询。本文件定义 KB 写入、管理及问题回流。
> 任务尚未做 KB-first 时,先按项目资源登记的实际命令查询。

### 11.1 模块知识库公共路由

> 本节只定义通用规则,不列具体模块名称、alias 或实例路径。项目级映射由项目资源文档、模块局部规则和项目内注册表提供;支持任意数量的模块。

1. 先明确本任务的 `<module-id>` 与 `<module-root>`。模块目录尚未实现时,使用已确认的项目级声明识别模块,不得假称已有自动登记。
2. 查找模块显式关联的 KB:优先读取已有模块目录的 `kb_aliases`,缺失时查模块局部规则或项目资源文档。生成目录仅是声明的投影;来源冲突时报告并询问,不得按优先级掩盖冲突。
3. 用项目内 `<PROJECT>/llm-wiki-aliases.json` 将 alias 解析为 `<kb-root>`;声明为路径时也须与注册项核对。注册表只负责 alias 到路径,不能单独证明模块归属。
4. 校验目标目录、`.wiki-schema.md`、KB 主题与任务归属。当前目录恰好是 KB 或存在 `<module-root>/knowledge/`,均不能代替模块关联确认。模块经验优先落入已关联的模块目录内 KB;共享 KB 必须有明确的项目级关联。
5. 无匹配项时报告缺少关联或未注册;目录无效、主题不匹配或多个候选无法判定时报告具体原因并询问。不得猜路径、回退全局注册表、自动创建 KB 或修改 alias。
6. 多模块问题按 §11.9 确定主记录与各模块记录;历史/参考类 KB 仅在主题明确匹配时选用,不得作为默认兜底。

执行 KB 操作时使用解析后的 `<kb-root>` 和已核实存在的项目 skill 脚本;只有包装脚本真实存在时才使用它。新建 KB 或改变关联须另有明确授权。

### 11.2 知识技能与插件接入

- 使用项目资源文档声明且本次真实可用的知识技能,先读 SKILL.md,再核实脚本/插件参数与副作用。
- 查询、摄入、状态、校验、图谱、整理与删除均由所选技能规定具体执行方式;不要从操作名推断无写入。
- 仅包装脚本真实存在时才使用它;否则采用已核实的入口和显式 KB 根。插件存在不代表目标库关联或写入授权成立。
- 不在此固定工具版本、安装路径或工作流数量;缺失时报缺口,不自动安装。

### 11.3 FeatureKnowledgePacket

```yaml
schema: feature-knowledge/v1
feature: <功能>
decision_supported: <当前要支持的决定>
user_goals: []
terms: {}
current_released_behavior: []
historical_decisions: []
compatibility_constraints: []
known_incidents: []
risks: []
uncertainties: []
sources:
  - kb: <知识库>
    page: "[[页面名]]"
    provenance: EXTRACTED|INFERRED
staleness:
  checked_at: <时间>
  possible_stale_items: []
```

**只保留能支持当前决定的内容。** 无法说明"删除后会导致什么明确失败"的页面,不进入 Packet。

### 11.4 读取边界
- 不加载完整知识库
- 不把检索结果原样复制给后续 Agent
- 不把 wiki 当成活跃 OpenSpec change
- 不用无来源的知识覆盖用户当前决定
- 高漂移事实保留版本、日期、来源
- 页面冲突 → 报告冲突,不自动拼成结论

### 11.5 写入授权

| 工作流 | 默认行为 |
|---|---|
| query / lint / status / graph | 只允许已核实的只读模式;实际会写文件/缓存的模式须按写操作确认 |
| ingest / batch-ingest / digest 写入 / crystallize / delete | 需用户明确意图 |
| 已解决问题回流(§11.9) | 主动询问本次内容与目标 KB,确认后写入 |

**用户要查询 ≠ 授权摄入。要总结 ≠ 授权 crystallize。**

局部 schema 中的“session 结束自动”或“fix 提交触发”只触发摄入询问,不得绕过本次写入确认。用户已明确授权本次内容和目标时直接执行,不重复询问。

### 11.6 来源/推理分离
- 从归档规格/发布说明/测试报告提取 → 标 `EXTRACTED`
- 会话综合/归纳/建议 → 标 `INFERRED`
- `INFERRED` **不能**被表述为真实发布事实
- 用户明确要求 crystallize 或按 §11.9 确认包含会话归纳的解决记录时,才写会话推理

### 11.7 发布后回流
```
OpenSpec archive
  → 发布说明
  → 最终验证摘要
  → 按 §11.1 路由并按 §11.5 确认写入范围
  → 来源文件摄入
  → 功能/工程页面更新
  → lint
  → 按目标规则及授权决定本地 commit
  → 单独询问是否 push
```

按知识主题划分内容(不要求实际建立这些库):
- **功能知识库**:归档的 Req/Scenario、已发布流程、最终兼容矩阵、设计理由、版本绑定摘要
- **技术工程笔记**:可复用的工具链配置、设备环境差异、传输故障复盘、Runner 经验
- **不回流**:当前 task、未确认假设、单次偶发日志、完整 CodeGraph 输出、**密钥/密码/Token/设备账号**、未发布的功能承诺

### 11.8 冲突处理
- wiki vs 活跃 OpenSpec → OpenSpec 控制当前变更,wiki 标待更新
- wiki vs 已发布产品行为 → 用发布证据修订 wiki,保留来源
- 功能 vs 工程库混淆 → 按"产品语义"或"跨项目工程经验"重路由
- 来源无法验证 → 保留不确定性,不定结论

### 11.9 已解决问题后的模块化知识回流

**触发与确认**:
- 每次问题达到已验证解决状态,在交付时主动询问是否摄入,不要求先发布或 OpenSpec 归档。同一问题在一次交付中询问一次;拒绝、暂缓或未回复时不写入,不阻塞修复交付。
- 用户接受且已验证有效的临时规避方案可以建议保存,但必须标明“临时规避、根因未消除”。未验证修复、推测、阻塞或纯计划不算已解决;用户另行要求记录时标明真实状态。
- 一次列明问题标识、涉及模块、全部拟写 KB alias/路径、各自保存内容与验证范围。确认覆盖本次列出的记录及必要的索引、日志等更新;新增目标或扩大内容范围须补充确认。无合适 KB 时先报告路由缺口,不自动建库。

**多模块归属**:
1. 根因在一个模块、影响多个模块:完整记录归根因模块 KB;其他模块仅在有独立可复用经验时保存本模块摘要与主记录引用。
2. 多个模块分别存在问题并修复:分别保存各自的现象、根因、处理与验证,使用同一问题标识相互关联。
3. 共享接口或协作流程问题:优先使用明确负责该接口的模块 KB,或已配置的项目级集成 KB;主归属不明时让用户选择。
4. 涉及模块不等于写入模块。共享结论保留一份主记录,其他记录引用它;不得把完整记录无差别复制到所有 KB。跨模块成功结论必须有相应集成验证证据。

**内容与执行**:
- 写入前读取目标 KB 的 `AGENTS.md`(如有)、`purpose.md` 与 `.wiki-schema.md`,检索已有记录以复用或补充,避免重复摄入;按其已声明的目录与页面类型保存。
- 记录共同问题标识、主归属与相关模块、问题和影响、环境/版本、根因及置信度、关键排查步骤与排除依据、实际修复或规避步骤、验证命令及结果、已知限制和证据引用。没有提交或缺少证据时明确说明,不得编造。
- 来源文件和验证报告的提取标 `EXTRACTED`;会话综合与推理标 `INFERRED`。用户确认保存解决过程可覆盖其中已说明的会话归纳,不要求用户额外复述工作流名称。
- 只保存脱敏后的必要过程和可复核引用,不得保存密钥、密码、Token、账号、个人信息、设备唯一标识或完整敏感日志。
- 完整摄入须完成 schema 要求的来源记录、知识页、必要索引/日志及相关校验。只复制 raw 或运行脚本成功不代表完成;检查目标 KB 的链接、来源和实际 Git 边界内的 `git diff --check`。
- 多 KB 分别报告成功、失败或待处理;失败时保留已写状态并说明,不自动删除已完成记录。部分成功不得报告全部完成。
- 本地提交遵循目标 KB 既有规则,只纳入本次授权变更;嵌套仓库逐一确认状态。远端 push 单独询问,摄入授权不包含创建 KB、修改注册表或推送。

询问示例:`本次问题涉及 <module-ids>。建议在 <主 KB alias/path> 保存完整记录,在 <其他 KB alias/path> 保存各自经验并关联同一问题标识。内容包括脱敏后的排查、根因、处理、验证和限制。是否按上述范围摄入?`

### 11.10 建立知识库与注册

1. 先确认用途、归属模块、主题边界、目标目录、alias 以及是否已有适合的 KB;共享库必须声明关联,不以历史库兜底。
2. 明确取得建库、目标位置和注册/关联修改的授权。普通查询、发现模块、修复问题或同意一次摄入均不自动授权建库。
3. 核对目标路径边界和已有内容,读取所选知识技能的初始化说明。目录非空或同名 alias 冲突时停止冲突操作,不覆盖。
4. 使用已核实的初始化入口和 schema,只在批准位置建立;按项目单源注册表登记 alias,在模块或项目资源声明其归属。两者职责不同,生成目录只反映声明。
5. 检查 schema、purpose、必要目录/索引和局部规则;验证 alias 解析及只读查询到达预期 KB。报告已建内容和未完成项,不把空库称为已摄入。
6. 后续摄入仍按本次内容授权进行;不注册到全局、不更改机器级插件/工具配置,不自动 push。

### 11.11 跨库检索与引用

跨库检索使用已核实的查询入口及明确目标集合;全库查询范围限于项目已注册的 KB。
页面间引用可以使用目标 schema 支持的 `[[KB名: 页面名]]`。这种标记是链接语法,不是查询命令;先验证 alias、页面及目标格式,不要把未支持的跨库链接当作已可解析。
