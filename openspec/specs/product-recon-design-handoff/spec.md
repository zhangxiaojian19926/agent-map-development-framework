# product-recon-design-handoff Specification

## Purpose

为产品观察进入普通开发流程提供受控交接，把有效的私有观察证据转化为可公开审阅、仍需人工确认的设计输入，同时保持来源可追踪、私有内容隔离以及既有规格和实现门禁不变。

## Requirements

### Requirement: 显式交接与既有流程兼容

系统 SHALL 仅在调用方针对已有自动逆向 ID 显式请求产品设计交接时读取产品观察视图并生成设计输入。系统 MUST NOT 因产品观察文件存在而自动交接，且 MUST 保持未使用该入口时的初始化、普通开发、逆向请求、观察执行、计划哈希和默认输出不变。

#### Scenario: 显式交接已有产品观察

- **WHEN** 调用方指定存在有效产品观察的自动逆向 ID 并授予当前草案写入权限
- **THEN** 系统只读取该 ID 的交接证据并生成待确认设计输入，不重新执行目标、工具或观察

#### Scenario: 未请求产品设计交接

- **WHEN** 调用方执行普通初始化、地图、资料、默认逆向或其他开发命令
- **THEN** 系统不读取产品设计交接状态，不生成设计输入，也不增加网络、安装或第三方依赖

#### Scenario: 不支持的命令组合

- **WHEN** 调用方将设计交接与新逆向请求、旧 scope、产品草案生成或其他互斥动作组合
- **THEN** 系统在目标执行和文件写入前返回明确输入错误

### Requirement: 来源绑定与证据新鲜度

系统 SHALL 在交接前验证 `product-recon/v1` 的结构、预算、逆向 ID、计划哈希、行为契约哈希、观察引用和证据 provenance。相关请求、计划、行为契约、观察记录或声明保留的原始证据缺失、篡改、跨计划、未成功或过期时，系统 MUST 拒绝交接并保留既有设计输入。

#### Scenario: 有效证据链交接

- **WHEN** 产品视图与当前请求、批准计划、行为契约及成功观察记录一致，目标与保留证据指纹未变化
- **THEN** 系统接受该来源并记录可复核的产品视图 SHA-256 和交接状态

#### Scenario: 篡改或过期证据

- **WHEN** 产品视图、行为契约、计划、观察记录、目标或原始证据与绑定指纹不一致
- **THEN** 系统返回可区分的过期或完整性错误，不生成或覆盖公开草案

#### Scenario: 不可用动态或静态观察

- **WHEN** 事实条目引用未授权、缺 provider、失败、未知或不属于当前计划的观察
- **THEN** 系统拒绝将其作为已观察产品事实交接

### Requirement: 脱敏设计输入与范围表达

系统 SHALL 将公开设计输入写入 `docs/project/design-input.md`，保留来源 ID、产品视图指纹、稳定 S/F/C/E ID、provenance、confidence、已观察/未观察状态和安全排除分类。公开草案 MUST NOT 复制私有名称、目的、步骤、字段、关系、排除原因、原始证据、URL、Cookie、Authorization 或账号正文。

#### Scenario: 私有产品草案含敏感内容

- **WHEN** 有效产品视图包含私有屏幕名称、流程步骤、实体字段、私有端点或排除原因
- **THEN** 公开设计输入仅包含固定结构与许可元数据，敏感自由文本仅留在原私有产物

#### Scenario: 部分事实与推断尚未覆盖

- **WHEN** 产品视图包含未观察状态、排除项或 `INFERRED` 条目
- **THEN** 设计输入明确保留这些边界和置信度，不把它们改写为已确认需求或已验证事实

### Requirement: 确定性交接与人工内容保护

系统 SHALL 对同一产品视图生成确定性设计输入和交接元数据，重复执行 MUST 幂等。系统 MUST 仅更新本能力针对同一逆向 ID 所有的草案；检测到人工修改、来源 ID 冲突、非法已有文件或交接状态不一致时 MUST 保留现状并请求核对。

#### Scenario: 相同来源重复交接

- **WHEN** 同一逆向 ID 的同一产品视图再次交接且草案与状态未改变
- **THEN** 文件内容与 SHA-256 保持稳定，不重复追加区块，结果报告未变化

#### Scenario: 同一来源产品视图更新

- **WHEN** 同一逆向 ID 产生新的有效产品视图且既有交接草案未被人工修改
- **THEN** 系统原子替换草案与交接元数据并报告更新，旧观察证据不被改写

#### Scenario: 人工草案或来源冲突

- **WHEN** 目标设计输入已有人工内容、其他逆向 ID 的交接内容，或交接后被人为编辑
- **THEN** 系统返回冲突，不覆盖、不删除也不合并这些修改

### Requirement: 只读预览与资源边界

系统 SHALL 支持 dry-run 预览来源校验、公开草案指纹和计划写入结果，dry-run MUST NOT 写入设计输入或交接状态。系统 MUST 限制输入字节数、嵌套深度和条目数量，超限、malformed JSON、符号链接或不可读文件 MUST 返回受控错误而非 traceback。

#### Scenario: 有效 dry-run

- **WHEN** 调用方对有效产品观察执行设计交接 dry-run
- **THEN** 系统返回来源状态、草案预览指纹和待确认状态，文件系统保持不变

#### Scenario: 非法或超限产品视图

- **WHEN** 输入 JSON 无法解析、超过预算、嵌套过深或经符号链接提供
- **THEN** 系统在公开草案写入前返回明确输入错误

### Requirement: 设计交接不替代规格批准与实现验证

系统 SHALL 将交接结果固定标记为 `NEEDS_DESIGN_APPROVAL`，并保持 `runtime_validation=NOT_RUN`、`source_map_evidence=False`、`implementation_approved=False`。系统 MUST NOT 自动创建、批准或归档 OpenSpec change，不自动生成 Req/Scenario、计划、业务代码、测试通过结论或发布就绪状态。

#### Scenario: 草案交接完成

- **WHEN** 系统成功生成产品观察设计输入
- **THEN** 下一步是用户审阅草案并进入普通 DISCOVERY 与 OpenSpec 流程，而非直接实施或验收

#### Scenario: 后续批准与开发

- **WHEN** 用户批准设计并选择实施范围
- **THEN** 后续工作仍须经过规格校验与批准、计划、TDD、评审和适用环境验证，交接记录不得充当完成证明

### Requirement: 可理解的交接结果与开发指南

系统 SHALL 在结果中区分来源校验、草案写入、设计批准和运行验证状态，并给出固定产物路径与下一步。开发指南 SHALL 说明逆向观察、产品设计交接、人工批准、OpenSpec 和业务目录之间的先后关系及公开/私有目录责任。

#### Scenario: 用户按指南接续开发

- **WHEN** 用户完成一次产品观察设计交接
- **THEN** 用户能够依据公开草案、固定结果和指南确认设计，再选择普通工程壳开发入口，无需手工计算内部哈希或复制私有证据

#### Scenario: 交接失败后的恢复

- **WHEN** 来源过期、证据缺失或目标草案冲突
- **THEN** 结果指出需要重新观察、恢复证据或人工核对的类别，不宣称部分草案已成功交接
