# debugging-discipline Specification

## Purpose

规定排障阶段的诊断纪律：什么算合法的红色信号、反馈回路如何建立并收紧、假设如何排序与证伪、插桩如何对应预测、修复后按什么 seam 写回归、以及何时停止尝试并质疑架构。技艺层来自上游参考，合规层为本框架本地改编，两者同属一个技能入口，不产生第二套完成判据。

## Requirements

### Requirement: 合法红色信号与环境故障的区分

系统 SHALL 要求在提出任何修复之前先建立一个能对目标 bug 变红的反馈回路，并按可判定的四条标准收紧它：能对该 bug 变红、结果确定、耗时在秒级、Agent 可无人值守运行。系统 SHALL 把环境故障（编译器缺失、设备不可达、网络中断、runner 异常）记为 INFRA_ERROR，不得当作合法红色信号，也不得当作通过的验证。

#### Scenario: 回路必须能对该 bug 变红

- **WHEN** 为某个 bug 建立反馈回路
- **THEN** Agent 命名出一条已实际运行过的命令，并说明它断言的是用户的具体症状而非"没有崩溃"

#### Scenario: 结果不确定或耗时过长

- **WHEN** 回路存在抖动或需要数分钟
- **THEN** Agent 继续收紧它：缓存准备、缩小范围、固定种子、隔离文件系统或网络，而不是接受一个慢而不稳的回路

#### Scenario: 环境故障被识别

- **WHEN** 失败原因是环境不可用而非行为缺失
- **THEN** Agent 记 INFRA_ERROR 并说明环境缺口，不把它写成有效红色，也不报告为验证通过

#### Scenario: 无法建立回路

- **WHEN** 确实无法构造出能变红的回路
- **THEN** Agent 明确停止并列出已尝试的手段与所需的用户提供物，不在缺少回路的情况下进入假设阶段

### Requirement: 排序且可证伪的假设

系统 SHALL 在测试任何假设之前生成多个排序后的假设，每个假设必须给出可证伪的预测，形式为"若 X 是原因，则改变 Y 会使现象消失或加剧"。系统 SHALL 在测试前向用户展示排序结果。系统 SHALL 一次只改一个变量。

#### Scenario: 假设必须可证伪

- **WHEN** 列出候选原因
- **THEN** 每条都写明改变什么会让现象消失或加剧；写不出预测的视为猜测，不进入候选

#### Scenario: 插桩对应具体预测

- **WHEN** 为区分假设而加日志或断点
- **THEN** 每个探针对应某条已列出的预测，且一次只改一个变量

### Requirement: 修复与回归测试的 seam

系统 SHALL 在修复前判断是否存在正确的 seam，即能复现真实 bug 模式的调用位置。系统 SHALL 先写回归测试再修复，并确认它因目标行为缺失而失败。系统 SHALL 在没有正确 seam 时把这一点记录为结论本身。

#### Scenario: 存在正确 seam

- **WHEN** 能找到复现真实调用链的测试位置
- **THEN** Agent 先在该 seam 写失败测试，确认失败原因正确，再实施最小修复并让测试通过

#### Scenario: 没有正确 seam

- **WHEN** 现有测试位置太浅，无法复现触发该 bug 的调用链
- **THEN** Agent 把"缺少正确 seam"作为结论记录下来，并说明这属于架构问题，交由设计环节处理，而不是写一个给虚假信心的测试

### Requirement: 清理与完成判据

系统 SHALL 在宣布修复完成前移除全部调试插桩、删除一次性原型，并复跑原始复现场景确认不再复现。系统 SHALL 记录已定位并成立的根因假设。

#### Scenario: 完成前清理

- **WHEN** 准备宣告问题解决
- **THEN** Agent 移除带调试前缀的插桩、删除临时产物，复跑原始场景确认不再复现，并记录成立的根因假设

### Requirement: 三次失败后的架构升级

系统 SHALL 在同一问题的第三次修复尝试失败后停止继续尝试，转而质疑架构是否成立，并把该判断与人类讨论。

#### Scenario: 连续三次失败

- **WHEN** 三次修复尝试都以相同方式失败
- **THEN** Agent 不启动第四次尝试，指出这属于架构信号并与用户讨论是否需要改变模块边界

### Requirement: 纪律层与证据绑定

系统 SHALL 保留无根因调查不修复的强制要求、合理化说法的逐条回应与禁止行为清单。系统 SHALL 要求诊断结论绑定到实际检查的工作树或提交与实际运行的命令；绑定到其他版本的结论只是假设。

#### Scenario: 结论必须绑定被检查的版本

- **WHEN** 形成根因结论
- **THEN** Agent 记录所检查的版本、产生信号的实际命令与其输出，且在变更后重新验证

#### Scenario: 合理化跳过过程

- **WHEN** 出现"先快速修一下再调查"等倾向
- **THEN** Agent 按对照表逐条回应并回到建立回路的阶段

### Requirement: 技能替换与引用一致

系统 SHALL 以新的调试诊断技能作为排障阶段的唯一入口，下线旧入口，并更新引擎内交叉引用、阶段路由、异常回流表与文档计数。

#### Scenario: 不再引用已下线的技能

- **WHEN** 检查引擎内技能引用、阶段路由、异常回流表与指南
- **THEN** 其中不再出现已下线的调试技能名称，历史归档与历史创作记录中的原有路径保持原样

#### Scenario: 随迁材料引用完整

- **WHEN** 检查新技能目录内的相对引用
- **THEN** 每一条指向同目录文件的引用都有对应文件存在，脚本通过语法检查
