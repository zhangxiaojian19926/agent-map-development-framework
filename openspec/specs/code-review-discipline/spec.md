# code-review-discipline Specification

## Purpose

规定评审阶段的方法纪律：评审沿哪些轴展开、规格从哪里来、规范基线是什么、结论绑定到什么范围、发现如何闭合，以及自查与独立评审如何区分。方法层来自上游参考，本框架适配层规定其在本框架内的来源与边界，两者同属一个技能入口。

## Requirements

### Requirement: 两轴分离且不互相掩盖

系统 SHALL 把规范符合性与规格符合性作为两条独立的轴分别评审并分别汇报。系统 SHALL NOT 合并两轴的发现或跨轴排序取舍。系统 SHALL 在规范轴同时应用仓库自身文档化的规范与固定的气味基线，且基线项一律记为判断项而非硬性违规。

#### Scenario: 一轴通过另一轴失败

- **WHEN** 变更完全遵循仓库规范但实现了错误的东西，或完全实现了要求但破坏了仓库约定
- **THEN** 汇报分别呈现两轴结果，不用任一轴的成功掩盖另一轴的失败

#### Scenario: 仓库规范优先于基线

- **WHEN** 仓库自身文档化的规范与气味基线对同一处给出相反判断
- **THEN** 以仓库规范为准并抑制该项基线告警，基线只用于仓库未作规定之处

#### Scenario: 基线项是判断项

- **WHEN** 报告基线类发现
- **THEN** 标注为可能的判断项而非硬性违规，并跳过工具已经强制的规则

### Requirement: 规格来源为当前变更

系统 SHALL 以当前 OpenSpec change 作为规格来源，读取其能力规格中的 Requirement 与 Scenario、任务清单中的切片与完成度，以及存在时的设计与提案。系统 MUST NOT 用提交信息或变更自述替代需求。系统 SHALL 在找不到变更时如实报告无可用规格并跳过规格轴。

#### Scenario: 规格从变更读取

- **WHEN** 评审某变更的实现
- **THEN** 规格轴以该变更的能力规格为准，并按 Requirement 与 Scenario 逐条核对

#### Scenario: 没有可用规格

- **WHEN** 找不到对应的变更
- **THEN** Agent 报告无可用规格并跳过规格轴，不以提交信息充当需求

### Requirement: 集成轴

系统 SHALL 对跨模块变更增加集成维度的评审，按该变更声明的接口责任与版本组合检查跨边界正确性。系统 SHALL 在单模块变更时显式说明跳过集成轴的理由，而不是静默省略。

#### Scenario: 跨模块变更被评审

- **WHEN** 变更涉及多个模块
- **THEN** Agent 按声明的版本组合评审跨边界行为，并记录该组合

#### Scenario: 单模块变更跳过集成轴

- **WHEN** 变更只涉及一个模块
- **THEN** Agent 明确说明集成轴被跳过及其原因

### Requirement: 范围与结论绑定

系统 SHALL 以变更的实际作用域确定评审范围，跨仓变更按各仓分别给出范围并记录版本组合。系统 SHALL 把每条评审结论绑定到实际评审的区间、规格版本与支撑命令。系统 SHALL 在范围变动后重新评审或标注失效部分。

#### Scenario: 结论绑定实际范围

- **WHEN** 给出评审结论
- **THEN** 结论指明所审的区间与所依据的规格版本

#### Scenario: 范围已变动

- **WHEN** 被评审的区间在评审之后发生变化
- **THEN** Agent 重新评审或明确标注哪些结论已不再覆盖当前代码

### Requirement: 问题闭合与自查标注

系统 SHALL 要求重要问题在继续推进前修复并重跑受影响的检查，次要问题可记录留待后续。系统 SHALL 把驳回的问题连同理由记录下来。系统 SHALL 把自查明确标注为自查，SHALL NOT 表述为独立批准；无独立评审可用时如实报告为限制。

#### Scenario: 重要问题闭合

- **WHEN** 评审发现重要问题
- **THEN** Agent 在继续前修复并重跑受影响的检查

#### Scenario: 没有独立评审

- **WHEN** 评审由执行者自己完成
- **THEN** 报告标注为自查，并说明未获得独立批准，不写成"评审通过"

#### Scenario: 驳回一条发现

- **WHEN** Agent 认为某条发现不成立
- **THEN** 记录驳回理由，而不是沉默地忽略该发现
