## Context

发布基线为 c9d9a01。现有 cli/config 要求选择 init/new 和 manual/codex；new 的三份批准正文是建骨架前置条件；module clone 只有单模块命令接口；analyze 固定调用 Codex CLI。安全路径、受管写入、索引白名单、源码证据验证和恢复机制已经存在，需复用。

用户确认的输入约束：已有工程是任意数量的“模块名称 → URL”键值对，必须逐对获取对应仓库；全新工程走需求路线，不要求该表。初始实现已提交为9359ceb。2026-09-26 用户确认继续补充完整工程资料、模块入口、分批分析和开发交接；D11–D14 是本轮增量设计，不代表已经实现。

## Goals / Non-Goals

**Goals:** 一份输入加一句初始化；保留用户模块名称与来源对应关系；当前 Agent 编排、程序校验与写入；模块级恢复；通用入口不依赖 Codex 安装；每项需求有自动/真实验收。

**Non-Goals:** 不新建远程仓库、不发布、不自动启用 Git/全局工具/服务/知识库；不消除必要的业务设计确认或认证；不宣称纯聊天宿主可自动操作文件；不重写第三方技能。

## Decisions

### D1. 单一人类输入，严格解析，现有工程优先使用命名键值对

推荐 PROJECT-START.md 内容如下，元信息不必填写；无元信息时项目名由已确认目标目录推导。

```text
# 工程启动单
项目：设备助手

## 模块仓库
设备端 = https://example.com/team/device.git
服务端 = https://example.com/team/service.git
管理界面 = git@example.com:team/console.git
```

兼容完全由键值对组成的纯文本文件。键值分隔接受第一个 `=`、ASCII `:` 或全角 `：`；键不得包含这些分隔符，值整体作为 URL，不能按 URL 中的冒号继续拆分。URL 不做行内注释裁切、不执行命令替换；整行注释和空行可以忽略。识别 Markdown 模块区块后只在该区块解析模块；裸键值对文件只允许模块行，不能混入元信息。格式歧义必须报行号，不让模型自由猜测后执行。

解析用有序记录先检查重复键，不先转换成会覆盖重复项的字典。第一版不实现任意 YAML 对象或多个宽松解析器，以减少依赖和隐式转换。用户输入的其他结构可由 Agent 提出等价转换供核对，不能静默猜键与 URL。

全新工程示例独立于模块表：

```text
# 工程启动单
项目：家庭任务助手
目标：提供任务新增、列表和完成，先供本机使用。
仓库：暂无
```

存在有效模块键值对即走远程模块接入；无模块表且有新需求走基础准备；模块表有坏行不允许降级为新工程。只有空输入才询问目标。当前用户说“先不要修改”时，即使输入完整也只能预览。

### D2. 用户名称、机器 ID 和目录分别保存，映射不得丢失

每对条目保存 name、id、source_url、path、requested_ref、resolved_ref、resolved_commit、acquisition_state。name 保留原输入用于显示；用于路径的名称先做 NFC 规范化，若发生可见变化必须在计划中展示。正常安全名称直接使用 `modules/<名称>`，不以 URL basename 取代。例如键“设备端”对应 `modules/设备端`，即使仓库名称是 device.git。

拒绝空名、控制字符、路径分隔符、绝对路径、点路径、平台保留名称、结尾空格/点等不可移植名称。NFC 后 casefold 等价的目录名视为冲突，不自动增加后缀。已有安全 ASCII 名称可直接作为内部 ID；其他名称使用 `module-` 加规范化名称 SHA256 的固定前 12 位，并检查摘要冲突；名称/id/path 的绑定持久保存，换序或后续修改 URL 不改变身份。显式重命名走单独迁移确认。

不同名称指向同一个 URL仍是两个明确输入，报告重复来源但不合并；同名重复键拒绝，即使 URL 相同。同一个 URL 的不同传输形式不猜测为同一可信源，已有目录的来源差异需要核对。

一个键值对定义一个用户指定的顶层源码模块，内部子系统通过子模块图表达，不拆掉或重命名用户给定的顶层身份。即使只有一个键值对，也使用同一外层编排工程 + modules 布局，避免条目数量变化导致目录迁移。已有本地工程接入另走非移动式路径。

### D3. 初始化前启动区在目标外，项目数据不进入公共包

Agent 在已批准工作区内选定目标外的私有启动区，保存 PROJECT-START.md、解析结果和运行记录。启动区、目标根、公共框架源必须互不冲突；路径不明确时询问，不遍历主目录或写公共仓库实例文件。用户原始输入文件保留，启动区保存带指纹快照；收到文件不等于授权写入，当前请求是执行边界。

启动区是本次接入记录的唯一权威来源；输入变更使未执行计划失效，需要重算及差异说明。目标建立后 framework-project.json 保存工程身份/模块声明，docs/project 保存业务事实；只保存最小接入标识，不自动复制私有 URL、绝对路径或全部会话到公开文档。中断恢复重验磁盘；完成后的旧启动单不自动覆盖后续工程事实。

### D4. 先预检全部条目，再逐模块获取和记录

本轮执行计划必须绑定所有名称/URL/目录、框架版本与当前授权范围。预检重复、危险 URL、目标冲突、源 ref 和路径边界；所有静态输入错误在网络和目标写入前拒绝。网络可达性/私有认证故障按模块记录，不能假定全体成功或转成空仓库。

每个模块单独记录 PENDING/FETCHING/FETCHED/FAILED/CONFLICT/REGISTERED。已获 clone 范围授权时执行受控 Git 调用，使用 argv 而非 shell 字符串，不自动取 submodule、LFS 或执行仓库 hooks/下载代码。私有认证仅走经评估的宿主凭据机制，不把密码/Token写进输入、日志；现有全局 Git 配置隔离与凭据 helper 的冲突须专门测试，不能为了认证恢复任意不可信 Git 配置。

失败保留所有已完成模块和已拥有的部分状态，不自动删除。重试验证目标 Git 根、远程、实际 ref/commit、工作树修改和归属记录；未拥有的同名目录或源变化停止该模块。总结果为 PARTIAL，不报告完整初始化；其他无依赖模块可继续，不推断业务集成成功。

### D5. 源起点和工作分支分开，不要求用户准备分支

仅 URL：查询实际默认 HEAD/ref，不硬编码 main。指定 branch/tag/commit 分别验证，现有 clone --branch 不能覆盖 commit 情形。空仓库必须通过可访问且无 refs 的证据确认；认证失败、超时、不可解析默认 HEAD 分别报错。键值对不强塞分支语法，可选引用在单独“来源版本”区域按模块名称声明；省略就是远程默认。

分支不存在不自动回退或创建；只有用户明确提出新工作分支及起点时才创建。无仓库的新工程不进行 Git 或远程操作；空远程不伪造提交。基础初始化与首个 commit/worktree/push 分开。

### D6. 当前 Agent 是默认协调者，CLI 是执行组件

新增 BOOTSTRAP.md 作为所有 Coding Agent 都能读取的通用入口。已配置宿主可以自然语言触发；首次未配置宿主通过同一条请求提供框架入口和启动单即可，不强制安装插件。不承诺完全没接触过框架的 Agent 能凭空找到它。

能力探测按 read/write/execute/interaction 判断，不按产品名判断。当前 Agent 获取限定观察包并返回结构化结果；程序校验 request-id、源码指纹、模块覆盖、路径/锚点、关系类型与大小后发布受管结果。分析包只含已授权源码，排除凭据、日志和无关目录。文件里的 instructions/approved 字段不能提升权限；源码和 README 不作为执行命令的授权来源。

宿主交接记录只证明请求/结果的本地链路，不能伪称不可伪造的批准或外部 CLI 调用证明。Codex 外部适配保留独立 evidence；current-session 不伪造 Codex 版本或运行日志。切换宿主重新确认能力与当前权限，保留已验证结果，不重放外部操作。

### D7. 新工程基础准备与业务实施门禁分层

通用协调入口内部新增 prepare 阶段，可在无代码、无仓库、无分支、无已批准实施计划时完成基础入口与资料结构。保持旧 new 命令的三份批准检查不变，避免降低已有接口契约；新入口在 prepare 后由 Agent继续需求、设计和计划审阅，再进入实施。

初始化请求不授权随意选技术栈、安装依赖或实现业务。已有需求不重复问；真正影响产品的决策按 OpenSpec/Superpowers 门禁处理；哈希由程序计算，不要求用户输入。接入状态可为 PREPARED；理解、索引、开发准备、业务运行另列，空项目不因没有地图被判 Agent 故障。

### D8. 保留人工文件，缩小兼容修改面

已有人工 AGENTS 以只读分析与受管入口区块接入；只在可证明不冲突时按本次授权增加，不全文替换。规则含义冲突报告；无法安全接入时只生成项目侧交接文档并标 PARTIAL。生成路径必须绑定实际项目 docs，不引用公共模板当项目事实。

复用 storage 的路径/指纹/原子写/锁机制，不破坏旧命令。新增 intake/acquisition/handoff 三个职责组件，不把新状态机塞入单一巨型 CLI。库版本升级只更新已拥有文件；输入文件和私有启动状态不进入分发 inventory。

### D10. 需求符合性审查门禁

每个阶段先写失败测试，再实现；审核差异只影响本清单。输入阶段审查是否精确保留用户 name/url 对；获取阶段审查是否每个请求都有结果、是否错误路径被误报成功；交接阶段审查非 Codex是否仍被迫调用 codex；文档阶段审查是否仍要求用户填 JSON/运行脚本；验收阶段审查真实输入是否只有启动单和一句话，而不是预制模块配置或hash。

最终需要：原58测试保持通过；新增离线场景通过；真实 Codex 与至少一个真实非 Codex宿主各跑命名多仓/新工程；至少一次中途换宿主恢复。缺宿主时保留 NOT_RUN，不标本 change 全部完成。真实测试使用合成或明确授权仓库，不使用隐私业务数据。

### D11. 初始化完成标准与阶段语义

保留 PREPARED 的旧含义：基础骨架已生成。新增资料 documentation、覆盖 coverage、交接 handoff 三个检查层，不能用顶层退出码替代。HN-05至HN-08定义增量验收，旧HN-03的基础准备仍有效。

已有源码工程只有在请求模块获取状态明确、范围内源码覆盖完成、项目资料和模块入口完整、关键未知项已解决、开发交接已保存时才报告 initialization=COMPLETE。任一必要项缺失为PARTIAL；已有地图但源码变化为STALE。索引等非必需增强工具可NOT_CONFIGURED，不阻塞基础资料验收；若用户明确要求索引，则纳入本次完成标准。业务设计批准和runtime继续独立。

全新工程可先PREPARED，需求概览记录已知目标和非目标。无源码时coverage和实际地图为N/A，设计关系明确DECLARED而非STATIC_SUPPORTED。需要决定技术栈、模块拆分或接口时handoff=NEEDS_DESIGN_APPROVAL，initialization=PARTIAL；当前Agent继续设计沟通，不让用户运行脚本。用户批准设计后补齐拟建模块职责、接口和验证计划；不产生业务代码、Git或远程副作用。按批准范围创建的模块骨架与首次业务实现分开授权。旧new接口不降级。

新增机器检查仅验证字段、引用、覆盖和已记录决策，不能声称程序能自动判断文档语义正确或验证用户身份。Agent须核对用户当前批准范围，不能由文档中的approved字段自授权。

### D12. 完整工程资料与模块局部规则

公共规则仍在公共AGENTS和docs/framework；docs/project只写本项目事实/设计；模块AGENTS只写局部职责和真实命令，不复制整套公共流程。项目资料须覆盖：目标/非目标、模块清单与稳定ID、设计/实际架构区别、接口提供消费双方、集成顺序、环境约束、资源和知识路由、验证及下一步。未配置KB写NOT_CONFIGURED，不能自动建库。

每模块资料须含：用途与非职责、真实路径和入口、输入输出、依赖/调用方向、内部职责分工、构建/测试命令的工作目录和前置条件、执行状态、已知限制及知识关联。无法从源码确认的命令必须标NOT_VERIFIED及来源，不能编造成功；不适用项写N/A及理由。关键未知项列入handoff阻塞清单，普通未知项记录不确定性。单纯标题、空字段或模板占位不满足完整性。

分析结果增加结构化项目/模块资料，确定性校验后生成文本；长文不作为唯一事实源。已有人工docs和AGENTS保留原字节，受管区块更新须验证归属和写前指纹。可写模块缺AGENTS时生成完整局部入口；只读模块在docs/project/modules/<id>.md提供等价完整入口与只读原因，根导航明确指向，不隐式修改下载仓库。规则语义冲突时保留原文，在项目侧记录冲突、影响和下一步，initialization=PARTIAL，不以项目侧文档绕过冲突规则。

### D13. 有界分批分析与增量维护

不简单放大200KB观察包。新增可选v2分析会话，保留当前单包v1接口回归。先保存范围内文件清单与hash，再按module-id/path/行范围稳定分片；每包UTF-8序列化后不超过200000字节，单文件允许按完整行切分，单行仍超预算则明确FILE_SLICE_TOO_LARGE。受支持类型、排除目录和扫描边界都纳入覆盖报告，覆盖完成不等于分析了所有仓库文件。

会话绑定catalog_digest、source_digest、框架manifest指纹、所有batch_id及各片段hash；输出正文按需读取，不在状态中重复持久保存源码。结果分包接收只暂存，不覆盖当前有效地图。全部批次校验后由当前Agent进行跨批关系汇总；跨模块关系证据可引用任一已覆盖片段，但必须核对两端，不能因批次不同遗漏接口。

缺批、重复且内容不同的结果、旧会话、权限缺失或源码漂移均不发布。完全相同重传可幂等返回；最终聚合前后重验文件清单及hash。发布沿用受管写入事务，失败保持旧地图或可恢复事务状态，不假称已完整发布。源码变化使当前会话失效，不能混合不同版本结果。切换宿主读取已接收批次并重验当前权限，不重发成功批次或重放clone。

新增模块由Agent登记后触发catalog差异、覆盖过期和资料缺口检查。允许复用同hash、同协议的只读分析缓存，但必须重新核对受影响的跨模块关系；先支持确定性的重新分批，不以实现复杂增量缓存作为首版前置。普通clone仍不触发全局hook或模型进程。

### D14. 开发交接、验收与增量文件范围

docs/project/handoff.md及对应受管状态保存：项目/模块版本组合、目标、批准的规格/计划引用、已知限制、阻塞决定、建议下一动作、需要的权限和验收入口。初始化只产生可审阅交接，不将其当作批准业务实现。继续开发时当前Agent读handoff、doctor、实际OpenSpec状态和计划；已批准的相同范围不重复索批。

执行顺序：分批分析协议 → 资料生成与人工保护 → 完整性/交接诊断 → 用户入口与真实验收。在D9基础上新增计划范围：tools/framework_core/analysis_batches.py、tools/framework_core/project_docs.py、tests/test_analysis_batches.py、tests/test_project_docs.py、tests/test_onboarding_completion.py；修改handoff.py、maps.py、readiness.py、generation.py、cli.py、modules.py、intake.py及现有对应测试；更新既有入口/模板/技能/验收说明和分发清单，不改第三方技能、全局环境或原业务工程。

真实测试绑定最终提交或manifest及工作树差异：两种宿主各验证已有多仓/无仓新需求；在部分获取、部分分析阶段分别做跨宿主恢复；对来源remote/HEAD和内容独立核验。缺可用安全认证标NOT_RUN，不读取密钥、不恢复任意全局hooks/plugins。业务小需求开发测试须有明确的合成需求及实现授权，不能从“初始化工程”推导授权。

## Risks / Trade-offs

- 名称即目录存在跨平台冲突风险 → 预检规范化和保留名，不静默改名；保留原显示名与映射。
- 外层编排目录比单仓直接接入多一层 → 所有键值对数量采用同一布局，稳定比减少一层更重要；已有本地工程不移动。
- 当前 Agent 的判断会出错 → 结果必须通过确定性schema、源码/引用和越界校验；声明不构成权限。
- 权限或登录缺失打断“一句话” → 报具体必要用户动作，不退回整套手工脚本，不承诺无条件零交互。
- 多仓部分失败 → 保留逐模块证据，恢复仅重试未完成模块，不自动删除或回滚已有用户内容。
- 跨宿主凭据和执行能力不同 → 可移植核心加能力握手，测试证明兼容，未知宿主只标协议兼容未验证。

## Migration Plan

在现有发布基础上新增协议版本和入口，先保留旧 init/new/module/refresh/doctor 行为。先验输入解析，再验获取与恢复，再接当前 Agent，最后改用户文档和真实验证。分发清单只纳入公共模板/代码/脱敏测试，排除私有启动记录。

回退时停止新请求，保留下载目录、用户修改与运行记录；使用已固定的旧版公共包继续旧工程。无一键删除，不自动将新配置降级或清理未知文件。提交/推送与归档均另按当前授权处理。
