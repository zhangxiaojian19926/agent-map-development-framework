## Context

两个上游技能管的是计划阶段的同一件事的两层：

| | superpowers `writing-plans` | mattpocock `to-tickets` |
|---|---|---|
| 性质 | 计划文档纪律 | 任务分解技艺 |
| 强项 | 文件结构映射、任务右尺寸、逐步粒度、占位符禁令、自查清单、计划文档头与任务块模板 | tracer bullet 垂直切片、阻塞边与任务图、expand–contract、切片粒度的人审 |
| 空白 | 不禁止水平切片；没有表达阻塞关系的结构 | 无计划文档格式；无占位符与一致性纪律；依赖 issue tracker 发布 |

本地技能的**计划评审模板**（`plan-document-reviewer-prompt.md`）也是独立资产。

## Decisions

**合并为一个技能，而不是并存两个。**
两个技能争同一个触发词时，Agent 需要做一次二选一判断。合并后一次读取即获得两层：`SKILL.md` 是分解技艺（怎么切、怎么声明阻塞、怎么处理宽重构），`plan-format.md` 是文档纪律（切片记什么、计划文档长什么样、什么算占位符）。

**切片与阻塞边写入 change 的 `tasks.md`。**
这是本次最实质的修正。本框架的 OpenSpec `tasks.md` 实际上已经是微步骤清单，而计划文档另存他处——任务状态分散两处。改为：切片（即带验收条件与阻塞边的工作单元）是 change 的任务，写在 `tasks.md`；计划文档是细节伴随物，只承载文件、接口、代码、测试命令，并在 change 内引用。**任务状态因此只有一处来源**，符合框架 §2 不另建竞争状态源的要求。

**阻塞边用内联表达。**
OpenSpec 的 `tasks.md` 是自由格式的 Markdown，任务条目形如 "- [ ] 1.1 …"。阻塞边以条目内的说明行表达（"阻塞于：无" / "阻塞于：1.1"），不引入新文件、新 schema 或第二个任务清单。

**计划文档位置本次不动。**
退役 `writing-plans` 后，工程壳自身仓库的实施计划目录名仍带上游名。改目录会牵动 `docs/maintainer/repository-layout.md` 的迁移对照、业务项目目录所有权表和框架升级指南，属于独立变更。本次合并后的技能把位置交回项目约定（"按项目约定存放，在 change 内引用"），目录命名另作清理。

**上游原文不改写，计划格式层单独成文并带来源声明。**
`SKILL.md` 保持上游字节不变，便于日后与上游比对。

**不带入 `agents/openai.yaml`。**
上游用它区分用户调用与模型调用，本次只做技能替换，不引入调用形态机制。

## Risks

- 切片语义从"微步骤"变为"垂直切片"，与既有 change 的 `tasks.md` 粒度不同。既有 change 已归档且任务已定义，不受本次影响；新 change 起按切片写。
- 切片写入 `tasks.md` 后，OpenSpec CLI 的任务进度统计会把每个切片算作一个任务。这是期望行为——切片的完成度就是任务完成度。
- 上游 to-tickets 假设存在 issue tracker 并发布到那里。本地改编以 change 的 `tasks.md` 替代发布动作，其余方法原样保留。

## Migration

技能入口总数不变（25 → 25）：superpowers 由 12 减为 11，matt-pocock 由 4 增为 5。引擎内交叉引用、阶段路由表、计划阶段步骤与文档计数同步更新。不涉及初始化、CLI、逆向与发布流程。
