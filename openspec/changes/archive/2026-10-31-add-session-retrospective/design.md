## Context

上游 `mattpocock/skills` 的 `retro` 是**用户调用型**技能：它要求用户显式要求复盘，不让 agent 主动发起。它的产出是"对 agent 工作环境的改进候选"，按七类组织并按严重度排序。

它与本框架已有的两件事相邻但不重复：

| | 已有 | retro 的位置 |
|---|---|---|
| 知识回流 | 把**已解决**的问题记进知识库（向后） | 复盘**为什么会绕远路**（向前） |
| 评审 | 对**一次变更**判断合规与符合规格 | 对**一段会话**判断环境哪里拖了后腿 |

## Decisions

**保留上游的用户调用形态，并连同 Codex 侧的声明一起引入。**
上游 `SKILL.md` 带 `disable-model-invocation: true`，`agents/openai.yaml` 带 `policy.allow_implicit_invocation: false`。只取前者会让该技能在 Codex 上仍被模型自动调用，语义就错了。因此**两份都取**——这使本框架第一次拥有真实的用户调用型技能，为调用形态机制提供前向试点，而不是先改全部既有技能。

**适配层只回答"这个框架的东西在哪"，不改方法。**
上游方法对任何仓库都成立；本框架需要补充的只是：规范在哪、��查有哪些、证据以什么为准、哪些路径是本仓库特有的。全部写进 `framework-rules.md`，上游原文保持字节不变。

**候选必须绑定证据，否则丢弃。**
上游方法本身有这条精神（"what did you do, what did the skill do, what did you expect"）。本框架把它写成硬要求：无法指向会话中具体证据的候选不记入清单。一份掺猜测的改进清单比没有清单更糟。

**结果落到 `docs/maintainer/retro-findings.md`，逐条标状态。**
维护者资料归 `docs/maintainer/`。每条候选标注"已做 / 已排期 / 待决定"，使复盘结论能一路追到后续改动，而不是停在文档里。

**检查入口写进适配层，避免重复发明。**
上游方法明确要求"先读仓库自己的检查命令"，否则会把已存在但未接线的检查当成新需求。本框架的检查入口是固定的几个命令，写进适配层让复盘直接指向它们。

## Risks

- 复盘容易变成发散的建议清单。适配层要求每条候选给出证据、动作与成本，缺证据的直接丢弃。
- 首个用户调用型技能会让"调用形态"这条规则只有孤例。检查一致性断言留到调用形态机制那一批统一加，本次只落地真实行为。
- 复盘记录本身会沉积。适配层要求逐条标状态，下一次复盘要处理上一次的"待决定"项，而不是并列堆叠。
