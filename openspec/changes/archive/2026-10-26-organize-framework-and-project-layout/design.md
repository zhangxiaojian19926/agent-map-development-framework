## Context

当前生成器按根文件和目录前缀复制公共包，能覆盖多数运行资源，但也会把维护者文档带入目标项目；当前升级流程也未定义如何清理“旧版本已复制、以后不再需要的受管文档”。另一方面，仓库已有稳定的 `skill/`、`tools/`、`docs/framework/` 路径、严格清单和大量相对链接，大规模改名会产生高迁移成本而收益有限。

既有项目还包含人工 `AGENTS.md`、`docs/project/` 正文、模块局部规则、知识库和未完成 OpenSpec change。目录整理必须沿用受管区块、文件指纹和正常归档门禁，不能以“整理”为由覆盖人工内容或补写不存在的验证证据。

## Goals / Non-Goals

**Goals:**

- 用低迁移成本的文档分层，让使用者和维护者分别获得清晰入口。
- 用显式运行时白名单控制新项目和升级项目的 `.agent-framework/` 内容。
- 为业务项目提供可直接查询的目录所有权、提交规则和开发流转图。
- 让目录治理具备合成项目回归、链接检查、清单检查和最终 CI 证据。
- 将历史资料整理与旧 change 的证据化解耦，避免一次性搬动造成状态失真。

**Non-Goals:**

- 不重写初始化协议、OpenSpec schema、知识库 schema 或模块目录数据模型。
- 不把 `skill/`、`tools/framework_core/` 等稳定路径仅因命名偏好而迁移。
- 不强制已有业务项目迁移源码，不预设业务技术栈或微服务拆分。
- 不在本变更中完成旧 change 所要求的真实宿主、私有认证、设备或部署验证。
- 不自动提交、推送、发布、归档旧 change 或摄入知识内容。

## Decisions

### D1：采用“新增分层优先、稳定路径保留”的文档结构

新增 `docs/guide/` 承载使用者指南，新增 `docs/maintainer/` 承载公共壳维护说明，新增 `docs/archive/` 承载已明确归档的历史资料。保留 `docs/framework/` 作为公共规则位置；`docs/project-intake.md` 等现行接口参考先保持原路径，避免同时修改大量协议链接。

README 只承担受众分流和最短入口，BOOTSTRAP 继续是唯一初始化步骤来源。历史资料可以先通过集中索引和醒目标识完成逻辑归档，再单独移动物理位置；每次移动必须同时修正链接、测试和清单。

备选方案是一次性建立 `guide/reference/maintainer/archive` 并移动全部文档。该方案不采用为首步，因为链接和清单 churn 大，而且不改善运行时行为。

### D2：运行时分发使用显式白名单，并处理旧受管残留

新目标项目的运行时集合由明确规则组成：

- 根入口与法律文件：`AGENTS.md`、`BOOTSTRAP.md`、`README.md`、`LICENSE`、`THIRD_PARTY_NOTICES.md` 和 `framework-manifest.json`。
- 运行资源：`skill/`、`templates/`、`tools/framework`、`tools/framework_core/`。
- 当前公共文档：`docs/framework/`、`docs/guide/` 以及初始化、输入协议、集成和高级 CLI 所需的具名现行文档。
- 明确排除：`tests/`、`.github/`、`docs/maintainer/`、`docs/archive/`、`docs/superpowers/`、`docs/verification/`、历史验收和发布专用文件。

白名单同时受 `framework-manifest.json` 指纹约束，不能读取未登记文件，也不能因新增文件位于已允许目录就静默改变运行时集合；新增运行资源必须在清单和测试中有明确体现。

升级已有目标时，对旧版本 `.agent-framework/` 中“以前由框架拥有、现在已不属于运行时”的文件执行有限清理：仅处理旧受管记录能证明归属的已知路径，只有当前哈希仍匹配旧受管版本时才允许删除；已被人工修改或归属不明的文件保留并报告冲突。不得递归清空 `.agent-framework/`，也不得触碰目录外文件。

备选方案是继续按目录前缀复制或升级时保留全部旧文件。前者会继续混入维护资料，后者会让新旧项目内容长期不一致，均不满足目标契约。

### D3：目录指南以所有权表为核心，不改变现有数据模型

业务项目指南使用统一表格描述每类路径的责任方、编辑方式、提交策略和完成证据。`docs/project/` 表示当前事实，OpenSpec 表示活跃变化和正式规格，知识库表示经确认的复用经验，`.framework/` 表示本机状态。

`module-catalog.generated.json` 等现有生成文件继续保持当前契约，本变更不拆分其稳定声明与本机观察字段，也不引入第二份竞争登记。若实际使用中出现本机候选频繁漂移，再另立变更处理。

新项目默认推荐单仓模块化结构和 `modules/<module-id>/`，已有项目继续按真实路径登记。跨模块契约由明确提供方负责；只有共享编排根本身具有独立责任时才在根级保存集成测试，避免产生无人维护的根目录代码。

### D4：历史资料与旧 OpenSpec change 分开收口

历史计划、验收文档的归档属于文档整理；旧 change 的任务状态和归档属于证据治理，两者不得合并成一次批量移动。

旧 change 逐项核对任务、最终提交或工作树、适用环境和验证证据。当前证据不足的保留未勾和 NOT_RUN；需要新验证的另列任务，不在目录变更里虚构完成。只有全部适用门禁满足后，才通过 `openspec-sync-specs` 和 `openspec-archive-change` 的正常顺序处理。

### D5：以合成项目行为测试和链接检查共同验收

文档测试验证受众入口、历史标识和实际相对链接；生成测试覆盖：

- 新项目只包含白名单运行时，且必要入口完整。
- 维护者资料和历史资料不进入目标项目。
- 重复初始化幂等，人工正文、模块规则和知识内容保持不变。
- 旧受管冗余文件仅在归属和哈希吻合时清理，人工修改产生冲突。
- 清单或白名单漂移得到明确失败。

最终验证沿用公共检查、完整单元测试、OpenSpec 严格校验、diff 检查和 Ubuntu/macOS CI。文档可读性另用场景走查核对，不把“文件存在”等同于“易用”。

## Risks / Trade-offs

- [白名单遗漏运行资源导致目标项目初始化或后续阶段失败] → 以完整合成初始化和开发入口测试覆盖必需资源，失败时指出缺失路径；不允许用减少检查来通过。
- [清理旧受管文件误删人工内容] → 仅处理 `.agent-framework/` 内旧记录明确拥有且哈希未变的文件，其他情况保留并冲突停止。
- [文档移动造成相对链接和清单大面积失效] → 分层分批迁移，先加导航再移动历史资料；每批运行大小写敏感链接检查和清单校验。
- [所有权指南与生成器实际行为漂移] → 指南中的关键路径由生成分发测试和只读诊断共同核对，变更生成行为时同步更新指南。
- [旧 change 收口扩大成真实宿主验收工程] → 将缺证据项明确保留，任何新增验证、外部访问或归档另行核对授权。
- [目录规范被误用于强制迁移已有业务源码] → 在模板和指南中明确“新项目默认、已有项目原位”，用既有项目测试保护原路径。

## Migration Plan

1. **基线与导航**：记录当前分发测试和链接基线；新增受众入口、目录所有权和业务开发指南，暂不移动现行协议与稳定工具路径。
2. **运行时收敛**：先补白名单缺失、禁止内容和旧受管残留的失败测试，再实现生成与升级规则；验证新项目、重复运行、已有项目升级和人工冲突。
3. **历史资料归档**：集中标记历史入口，分批移动历史计划与验收资料，逐批修正链接、清单和文档导航。
4. **旧 change 对账**：仅核对实际证据并报告缺口；满足门禁的 change 另行按正常同步、归档流程处理，未完成项保持原状态。
5. **最终验收**：运行公共检查、完整测试、OpenSpec 严格校验和合成目录场景走查，在 Ubuntu/macOS CI 通过后交付。

回滚按阶段和提交边界进行：文档迁移回滚对应文档提交；运行时回滚恢复上一版公共包及白名单，不回滚或删除业务项目人工内容。若升级过程中发生归属冲突，保留现场并停止该目标项目升级，不以强制覆盖完成迁移。
