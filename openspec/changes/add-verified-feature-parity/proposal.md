## Why

产品观察和设计交接已经建立，但实现后的差距仍可能由 Agent 自报完成度、文件存在或单一测试退出码判断，无法可靠追踪“目标 → 已批准 Scenario → 任务 → 真实验证证据”。第三阶段需要一个不采用主观分数的证据驱动报告，明确哪些功能已验证、未运行、失败或仍有范围缺口。

## What Changes

- 增加显式功能差距报告入口，读取有效产品观察、指定 OpenSpec change 的规格与任务，以及结构化验证证据，生成可追溯的公开报告。
- 以当前文件哈希绑定输入；分别推导目标证据、实现和验证状态，拒绝非法状态、重复或无法追踪的 ID、过期证据及伪造的通过结论。
- 要求已批准规格中的每个 Scenario 都被覆盖或有明确非必须排除；缺失必须 Scenario、验证失败、未运行及按策略开放的 S1/S2 问题不能被报告为通过。
- 报告只展示可追踪状态、差距和证据索引，不使用 `clone=yes`、主观完成百分比或总分替代验收；视觉、可访问性和品牌诊断只作为独立证据类别。
- 支持 dry-run、确定性重复生成、合法更新与失败时旧报告保护；普通开发、逆向观察和既有 OpenSpec 状态不因未使用该入口而改变。

## Capabilities

### New Capabilities

- `verified-feature-parity`: 将产品目标、已批准 OpenSpec Scenario、实现任务和真实验证证据绑定为可复核的功能差距报告及门禁。

### Modified Capabilities

无；本变更不修改既有产品观察、设计交接、OpenSpec 审批或验证状态语义。

## Impact

- 影响框架 CLI、新增标准库差距报告模块、验证证据契约、公开 `docs/verification/` 报告、相关指南和离线契约测试。
- 不引入第三方依赖、上游 `replica/` 目录、自动业务实现、截图理解、品牌扫描、网络访问或部署行为。
- 保留 `add-completion-summaries` 等既有未提交工作；未显式运行差距报告的项目不产生新文件或新授权要求。
